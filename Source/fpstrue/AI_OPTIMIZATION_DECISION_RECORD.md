# AI 敌人系统优化决策记录

## 1. 优化目标

当前优化不是为了堆叠 Behavior Tree、EQS、感知等功能，而是解决现有敌人系统已经暴露出的工程问题：

- 敌人使用 `Tick` 持续计算距离、旋转和追击，敌人数量增加后 Game Thread 开销会近似线性增长。
- 敌人通过 `AddMovementInput` 直接朝玩家移动，不能可靠绕过墙体和复杂障碍。
- 追击、攻击、受击、死亡由多个布尔变量共同控制，存在状态冲突和中断清理风险。
- 多个敌人以同一个玩家坐标为目标，容易拥堵、重叠并同时攻击。
- 目标、Timer、EQS 请求、攻击槽位和死亡对象需要统一管理生命周期。
- 目前缺少固定场景、Baseline 和优化前后数据，无法证明方案真实有效。

最终目标是形成一条可以复现和解释的工程链路：

```text
发现逐帧直线追击的问题
→ 拆分决策、导航和战斗职责
→ 接入感知、NavMesh 和显式 FSM
→ 使用 EQS 解决战术站位
→ 治理异步请求与对象生命周期
→ 通过分级调度降低 CPU 开销
→ 用固定压力测试验证收益和响应延迟
```

## 2. 为什么先优化 AI

AI 同时涉及 Gameplay Framework、状态机、导航、空间查询、异步回调、对象生命周期和 CPU 性能。相比继续增加武器或 UI，它更适合作为 FPS 项目的核心技术深度：

- 能解释系统为什么这样拆分，而不只是展示功能清单。
- 能构造 `10 / 25 / 50 / 100` 个敌人的可重复压力场景。
- 能同时产出架构图、状态图、Bug 复盘、Insights Trace 和前后数据。
- 现有攻击窗口、伤害和健康系统可以继续复用，不需要推翻已经完成的战斗链路。

## 3. 架构优化

### 3.1 当前问题

`EnemyCharacter` 同时承担目标查找、决策、移动、攻击、受击和死亡，职责过多。直接移动还会与攻击动画、受击中断和死亡状态争夺角色控制权。

### 3.2 方案

```text
GameMode
负责波次、生成、游戏结果和全局战斗节奏

EnemyAIController
负责感知、目标选择、FSM、导航和 EQS 请求

EnemyCharacter
负责移动载体、动画、攻击窗口、伤害和死亡表现

HealthComponent
负责生命值计算和健康事件
```

### 3.3 原因

- Controller 表示“决策者”，Character 表示“世界中的身体”，符合 UE Gameplay Framework 的职责边界。
- 导航失败、目标变化和感知回调集中在 Controller，避免 Character 继续膨胀。
- 战斗和动画仍保留在 Character，已有攻击窗口代码不需要重写。
- 后续替换 FSM、Behavior Tree 或测试不同决策策略时，不影响伤害系统。

## 4. 显式 FSM

第一版状态：

```text
Idle
→ Chase
→ Attack
→ HitReact
→ Dead
```

优化原因：

- 多个布尔变量可能产生非法组合，例如“正在攻击且已经死亡”。
- 显式状态可以规定唯一入口、出口和允许的转换。
- 状态退出时可以统一清理 MoveTo、Timer、攻击窗口和槽位。
- 状态转换可以记录日志并建立测试矩阵。

每个状态必须定义：

- 进入时做什么。
- 持续期间允许什么。
- 退出时清理什么。
- 可以转换到哪些状态。
- 被受击、死亡、目标失效时如何中断。

## 5. AIController 与 NavMesh

### 当前问题

`AddMovementInput` 只提供期望移动方向，不负责全局路径规划。遇到墙体、不可达区域或复杂通道时，敌人可能原地顶墙。

### 优化方案

- 使用 `MoveToActor` 或路径跟随请求。
- 使用 NavMesh 计算可达路径。
- 通过 `OnMoveCompleted` 处理成功、失败和不可达。
- 只有目标位置变化超过阈值或状态改变时才重新请求路径。
- 进入攻击、受击和死亡状态时停止当前移动。

### 原因

- 将“去哪里”与“沿路径怎么移动”分离。
- 避免每次决策都重复提交相同路径请求。
- 可以统计路径请求次数、失败率和到达时间。
- 为 RVO、Detour Crowd 和 EQS 站位提供导航基础。

## 6. 感知系统

计划接入：

- Sight：看到玩家后进入追击。
- Hearing：枪声产生刺激，敌人前往声源或最后已知位置。
- Damage：受伤后锁定有效伤害来源。

优化原因：

- 当前敌人直接获得玩家引用，相当于始终知道玩家位置。
- 感知事件只在刺激变化时触发，比每帧主动搜索世界更合理。
- 最后已知位置和刺激过期能够形成可解释的目标记忆。
- 感知数据可以驱动 FSM，不要求立即引入 Behavior Tree。

需要处理的边界：

- 多个刺激源同时出现时如何选择目标。
- 目标死亡或离开世界后如何清理引用。
- 刺激过期后何时退出 Chase。
- 旧感知回调不能覆盖更新后的 Dead 或 HitReact 状态。

## 7. EQS 战术站位

第一版只实现一个查询：玩家周围攻击槽位选择。

```text
生成玩家周围候选点
→ 过滤 NavMesh 不可达点
→ 过滤已占用点
→ 按路径成本、距离和敌人间距评分
→ 选择最佳攻击位置
```

优化原因：

- 所有敌人追逐同一坐标会产生拥堵和重叠。
- 只依赖局部避障不能保证合理的战斗站位。
- 限制同时攻击者数量可以改善战斗可读性和伤害节奏。
- 单个真实查询比堆叠多个演示性质的 EQS 更容易验证和解释。

技术风险：

- EQS 是异步结果，返回时敌人可能已死亡或切换状态。
- 槽位必须在死亡、受击、中断和目标失效时释放。
- 查询不能每帧运行，需要冷却和重新查询条件。

## 8. 决策降频与错峰

建议初始分级：

```text
近距离战斗：0.10 秒决策一次
中距离追击：0.25 秒决策一次
远距离敌人：0.50～1.00 秒决策一次
远距离且不可见：休眠或极低频更新
```

每个敌人的首次更新时间加入随机偏移，避免同一批敌人在同一帧同时更新。

优化原因：

- 大部分 AI 决策不需要与渲染帧率相同。
- 100 个敌人每帧同时计算会形成 Game Thread 尖峰。
- 错峰只能降低峰值，分级更新才能减少总计算量，两者作用不同。
- 近距离仍保留较高频率，避免攻击反应明显迟钝。

必须同时记录响应延迟。不能只证明 CPU 下降，却忽略敌人进入攻击范围后反应变慢。

## 9. 群体避障

候选方案：

- RVO：接入简单，适合先建立对照。
- Detour Crowd：结合路径走廊，可配置性更高。

两者二选一，不同时启用。

比较指标：

- 25 和 50 个敌人通过狭窄区域的到达率。
- 拥堵和相互穿插次数。
- 平均到达时间。
- Game Thread 开销。
- 是否出现离开 NavMesh 或局部抖动。

不预先认定 Detour Crowd 一定更好，最终选择由项目场景和测试数据决定。

## 10. 对象与内存管理

重点检查：

- AI 目标失效后是否及时清理。
- Timer 是否在死亡和销毁时停止。
- 感知、Delegate 是否重复绑定或未解绑。
- EQS 回调是否访问已销毁敌人。
- 攻击槽位是否在所有中断路径中释放。
- 尸体、Niagara、Decal 和临时 Widget 是否按生命周期销毁。
- 连续波次后 Actor、UObject 和内存是否持续单调增长。

当前不直接实现通用对象池，原因是：

- 对象池会增加重置状态、引用残留和复用错误的风险。
- 敌人 Actor 的构造销毁未必是当前主要瓶颈。
- 先测量 Spawn/Destroy 尖峰和内存变化，再决定是否池化敌人或短生命周期特效。

## 11. 性能验证方案

固定测试场景：

```text
10 / 25 / 50 / 100 个相同敌人
相同出生点布局
相同运行时间
相同分辨率和画质
相同玩家路径或固定测试脚本
```

版本对照：

```text
Baseline：逐帧 Tick + AddMovementInput
版本 A：AIController + NavMesh + 显式 FSM
版本 B：Timer 决策
版本 C：距离分级 + 错峰更新
版本 D：EQS 攻击槽 + RVO 或 Detour Crowd
```

记录：

- Game Thread、Frame Time 和尖峰帧。
- AI 核心函数耗时。
- 每秒决策次数。
- 路径请求次数与失败率。
- EQS 查询次数和耗时。
- 进入攻击范围后的平均、最大响应延迟。
- 连续波次前后的 Actor、UObject 和内存变化。

工具：

- `stat unit`
- `stat game`
- Unreal Insights
- `TRACE_CPUPROFILER_EVENT_SCOPE`
- `stat memory`
- `memreport`

## 12. 停止条件

达到以下标准后停止继续扩展 AI：

- 敌人能够绕开静态障碍并处理不可达路径。
- FSM 的攻击、受击、死亡中断测试通过。
- 感知能够正确获得、遗忘和切换目标。
- EQS 攻击槽能够减少拥堵并限制同时攻击者。
- 完成至少 `10 / 25 / 50 / 100` 敌人的对照数据。
- 完成一份 CPU 优化报告和一份生命周期审计。
- 能解释方案收益、响应延迟和调度开销。

第一版不以 Behavior Tree、复杂 EQS、GOAP、多线程 AI 或通用对象池作为完成条件。

## 13. 面试表达主线

```text
旧实现的问题不是“敌人不够聪明”，而是决策、移动和战斗职责耦合，
并且所有敌人按渲染帧率同步更新。

我先用 AIController、NavMesh 和显式 FSM 修正架构与导航，
再用感知替代敌人始终知道玩家位置的逻辑，
用 EQS 攻击槽解决多敌人争抢同一目标点的问题。

最后通过距离分级、错峰更新和路径请求节流降低 Game Thread 开销，
同时记录响应延迟，避免用牺牲玩法响应换取表面上的帧率提升。

对象池没有预先加入，因为先做生命周期和 Spawn/Destroy 测量，
只有数据证明存在尖峰后才决定池化范围。
```
