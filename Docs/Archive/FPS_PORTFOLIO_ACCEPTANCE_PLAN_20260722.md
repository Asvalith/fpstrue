## 2. 完整游戏闭环

必须完成：

- 角色移动、瞄准、射击、换弹与死亡。
- 武器拾取、弹药管理、后坐力和随机弹道。
- 敌人受伤、攻击、死亡与行为终止。
- HUD：准星、血量、当前弹药、备用弹药和剩余敌人数。
- 胜利、失败和重新开始。
- 一局游戏可以从开始稳定运行到结算并再次开始。

闭环是验收底座，不作为唯一技术亮点。

## 3. 核心技术深度锚点

### 3.1 锚点一：战斗、动画与生命周期一致性

重点解决：

- 多状态冲突。
- 换弹中死亡。
- Montage 中断。
- AnimNotify 延迟、重复或未触发。
- Timer 残留。
- 弹药重复结算。
- 武器被丢弃后的回调。
- 重复死亡事件。
- Delegate 重复绑定、未解绑与对象销毁。
- Gameplay 状态与动画状态的权威关系。

必须能够比较：

| 对比项 | 必须回答的问题 |
| --- | --- |
| 多个布尔变量 / 显式状态机 | 如何表示互斥状态，非法组合如何被阻止 |
| Timer / AnimNotify 结算 | 规则结算是否依赖动画资源，Notify 丢失时如何兜底 |
| Character / Weapon 状态 | 谁拥有战斗状态，双方如何避免重复权威 |
| Tick 查询 / Delegate 通知 | 更新频率、调用关系和生命周期成本如何取舍 |
| 强引用 / 弱引用 | 谁拥有对象，谁只观察对象，对象销毁后如何失效 |

#### 状态测试矩阵

至少覆盖：

| 初始状态 | 事件 | 预期结果 |
| --- | --- | --- |
| Idle | Fire | 进入射击并只扣除一次弹药 |
| Firing | Reload | 按设计拒绝或中断射击后换弹 |
| Reloading | Fire | 不产生伤害和重复扣弹 |
| Reloading | Death | 中断 Montage、Timer 和弹药结算 |
| Reloading | Drop Weapon | 旧武器不再回调角色 |
| Dead | Fire / Reload | 所有战斗输入无效 |
| Dead | Damage | 不重复广播死亡事件 |

每个用例记录输入、状态转换、弹药变化、事件次数和最终结果。

### 3.2 锚点二：多敌人 AI 与 Game Thread 性能

建立固定压力场景，测试：

- 10 个敌人。
- 25 个敌人。
- 50 个敌人。
- 100 个敌人。

比较：

- 每帧 Tick。
- 固定更新间隔。
- Timer 更新。
- 错峰更新。
- 根据距离、可见性和战斗状态分级更新。

记录：

- Game Thread 时间。
- AI 核心函数耗时。
- 每秒更新次数。
- 平均和最大响应延迟。
- 总帧时间。
- 优化方案自身的调度开销。

必须解释：

- 降低更新频率为什么会产生响应延迟。
- 近距离战斗对象为什么需要高频更新。
- 分帧为什么可以降低峰值而不一定降低总工作量。
- 为什么不能简单关闭所有 Tick。
- 当前阶段为什么不优先引入多线程。

#### 固定基准方法

- 固定地图、出生点、敌人配置、分辨率和画质。
- 每组先预热，再采样固定时长。
- 每组至少运行三次，报告中位数并保留最大值或 P95。
- 使用 `TRACE_CPUPROFILER_EVENT_SCOPE` 标记核心 AI 路径。
- 性能修改前后使用相同提交、配置和测试脚本以外的条件。
- 原始 trace、统计表和机器配置一并保留。

## 4. 内存与对象生命周期

重点检查：

- Timer 是否在死亡、武器丢弃和销毁时清理。
- Delegate 是否重复绑定或未解绑。
- 武器引用、AI 目标和 HUD 对象是否失效。
- UObject、`UPROPERTY`、`TObjectPtr` 和 `TWeakObjectPtr` 的使用边界。
- Niagara、Decal、音效、尸体、武器和临时 Widget 的生命周期。
- 连续战斗后对象数量是否持续增长。
- 重启关卡后是否残留状态或对象。

工具：

- Unreal Insights。
- `stat memory`。
- `memreport`。
- Actor / Object 数量统计。
- Size Map 和 Reference Viewer。

固定实验：

```text
记录初始内存和对象数
→ 连续战斗
→ 高频生成特效和死亡对象
→ 记录峰值
→ 停止操作并等待生命周期结束和 GC
→ 再次记录
→ 重启关卡后复测
```

验收关注是否存在无法解释的单调增长，不预先承诺固定下降比例。

本轮不做：

- 自定义内存分配器。
- 通用对象池。
- 在没有性能证据时强行池化。

## 5. 图形表现与 GPU 分析

功能范围：

- 枪口火焰。
- 命中特效和命中声音。
- 墙体弹孔与敌人血迹。
- 物理表面差异化反馈。
- 受伤后处理与低血量提示。
- Custom Depth 拾取轮廓。

重点处理：

- 世界静态表面与 Skeletal Mesh 的命中差异。
- 移动敌人身上的贴花附着。
- 世界空间和组件空间转换。
- 特效、贴花和临时组件的数量及生命周期。
- 敌人销毁后的资源清理。

GPU 工具：

- `stat gpu`。
- ProfileGPU。
- Shader Complexity。
- Quad Overdraw。
- Niagara 调试工具。

固定比较：

- 无特效 / 正常特效。
- 正常射击 / 高频射击。
- 不同 Decal 数量。
- 不同 Niagara 数量。
- 后处理关闭 / 开启。

记录真实 GPU 时间、主要 Pass 开销、测试分辨率和画质设置。

## 6. 工程证据

### 6.1 Bug 复盘

至少完成三份：

1. 换弹状态无法退出。
2. 移动敌人贴花位置错误。
3. 死亡后 Timer 或 Delegate 继续回调。

每份必须包含：

- 现象。
- 复现步骤。
- 初步判断。
- 日志、断点或 trace 证据。
- 根因。
- 修复方案。
- 回归测试。
- 原方案为什么错误。

### 6.2 定量结果

必须产出：

- AI 优化前后数据。
- HUD Tick 与 Delegate 的调用次数比较。
- 连续战斗前后内存与对象数量。
- 特效和后处理的 GPU 数据。
- 战斗状态测试矩阵及通过情况。

所有数据必须能通过固定场景和步骤重复获得，不填写估算或虚构结果。

## 12. Git 提交门禁

提交历史本身属于工程交付物，必须真实反映问题、实现和验证过程。

### 12.1 基本原则

- 一个提交只表达一个技术意图，不混合功能、重构、资产和文档整理。
- 不按日期制造空提交，不修改作者时间伪造开发节奏。
- 不为了让贡献图均匀而拆分没有独立意义的提交。
- 已经推送的公开历史不随意改写；后续历史从当前节点开始保持严谨。
- 每个代码提交必须能够编译，并完成与改动范围相符的验证。
- 性能优化先提交可复现的 Baseline，再提交实现，最后提交复测数据。
- Bug 修复必须能够对应复现步骤、根因和回归结果。
- 不使用 `git add .`；始终按明确路径暂存并检查文件清单。

### 12.2 分支命名

使用自然、可读的任务名称：

```text
feature/combat-state
feature/enemy-fsm
feature/gameplay-loop
fix/reload-death
fix/decal-attachment
perf/ai-update-budget
perf/effect-lifetime
docs/portfolio-evidence
```

不使用工具名称作为公开分支前缀。

### 12.3 提交信息

格式：

```text
<type>(<scope>): <imperative summary>
```

允许的主要类型：

- `feat`：可验证的新功能。
- `fix`：具有根因和回归验证的修复。
- `refactor`：不改变外部行为的结构调整。
- `perf`：有 Baseline 和复测结果的性能修改。
- `test`：自动测试、压力场景或测试矩阵。
- `docs`：架构、报告、复盘和面试材料。
- `build`：构建、依赖和工程配置。
- `chore`：无法归入以上类型的必要维护。

示例：

```text
feat(combat): add explicit reload and death transitions
fix(lifecycle): clear enemy attack timer on death
test(ai): add fixed 50-enemy benchmark scenario
perf(ai): stagger decision updates across frames
docs(perf): record AI baseline and optimized results
```

需要说明取舍或验证时，在正文写明：

```text
Why:
- 问题和原方案限制

What:
- 本提交的具体修改

Test:
- 编译、PIE、状态矩阵或性能场景结果
```

### 12.4 提交前检查

每次提交依次执行：

```text
1. git status --short
2. git diff -- <target files>
3. git add -- <explicit files>
4. git diff --cached --check
5. git diff --cached --stat
6. git diff --cached
7. 执行对应编译、测试或基准
8. git commit
9. git show --stat --oneline HEAD
10. git status --short --branch
```

只有文件范围、验证结果和提交信息都正确后才推送。

### 12.5 文件边界

以下内容不得与源码功能提交混合：

- `Binaries/`、`Intermediate/` 和 `Saved/` 中的生成文件。
- 编辑器个人配置、临时缓存、日志和崩溃文件。
- 未确认用途的 `.uasset`、测试资源和下载素材。
- 简历草稿、冲刺计划和代码功能修改。

资源、代码、测试、性能报告和文档可以互相关联，但必须按独立意图组织提交。清理已经被 Git 跟踪的生成目录时，使用专门的仓库治理分支和独立提交，不与功能开发混合。
