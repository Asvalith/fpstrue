# FPS 网络设计、预算与验收

本项目只维护同一套多人 PvPvE 战斗规则。网络目标分别是本地操作响应、服务器裁决一致、有限弱网下的确认时延和明确负载下的资源预算。某项功能测试通过不代表其他目标通过；未运行、失败和无测量值必须单独保留。

## 运行合同

- CMC 继续管理移动预测、确认和重放；SavedMove 只扩展瞄准/冲刺模式，不在移动重放中再次激活技能。
- 权威弹药保存在 WeaponComponent，拥有者显示由权威基准与未确认输入派生。快照声明已包含的射击水位，不能先扣本地弹药、收到快照后又扣同一批输入。
- 换弹立即本地预测播放，GAS 接纳和服务器换弹快照接管原播放实例。拒绝、死亡、换枪和旧回调只能结束自己所属的动作；服务器时钟是唯一装弹入口。
- 射击身份绑定真实 Weapon Actor、Avatar、装备代际、开火轮次和 ShotId。同编号不重复执行，旧枪的请求不能借当前枪回复或扣弹。
- 当前网络协议版本为6，由 UE 原生网络握手检查兼容性。本轮删除无人消费的公共射击快照字段；旧 Cook/Stage 客户端需要一起重建，不增加双协议兼容分支。
- 命中查询保存玩家历史形状并插值求交，不临时移动真实物理世界。静态与动态遮挡、AI 使用当前碰撞；当前关闭的门可以阻挡历史玩家，门已打开则按当前开口判断。这是明确的玩法政策，不声称完整世界回滚。
- 联网玩家复用 CMC 的 Linear 平滑与原生变换时间戳。服务器在 Actor 更新结束、复制前采集历史，并把原生变换时间戳绑定到该历史样本。射击最多携带16名已接收副本的显示年龄（弱对象身份与毫秒差），不上传位置、碰撞体、伤害或命中结论。服务器逐目标验证身份与时效，查询该目标对应时刻；重复、异世界及非法年龄不能借元数据取得授权。
- 玩家模拟副本采用快照插值，停止额外的 `MoveSmooth` 速度前推；拥有者的预测/重放和服务器物理保持 CMC 原有路径。只改 Linear 参数而继续前推时，原生纠正时间戳仍不能代表最终显示位置，实测首发仍漏判。该取舍让时间与位置对应，但长丢包间隙可能短暂停留；Root Motion 与动态移动基座继续原生模拟，并明确不提供此显示时间证据。
- 新副本尚无有效显示时间时，才使用服务器 RTT/2 与 `GameMode.TargetInterpolationSeconds`（默认50ms、范围0–100ms）的估计回退。`bEnableTargetLatencyCompensation` 只控制回退的 RTT 项。已有原生显示时间若超出350ms历史，则该目标查询失败，不能换到更近时间凑命中；射击准入、未来容差、执行年龄与传送断代不放宽。
- 原生 Linear 允许短暂外推，报告给命中查询的时间保守限制在已发布样本内。这对应服务器根变换时间线，不保证客户端自行求值的每块骨骼、每个动画相位与服务器完全一致；不声称完整的逐像素 what-seen 回放。当前服务器预算为30Hz、历史最多60Hz。
- 全局 Gameplay Significance 保护所有玩家需要的权威更新。逐连接原生排序对该观察者正在交战的敌人加权，保留原生相关性、距离和等待时间补偿，不将其他连接的相机评分复制过来。
- 重连恢复同一服务器进程、本局内保留的真实 Pawn/PlayerState/装备。离线继续受伤，死亡照常结算；不恢复服务器重启或跨服状态。

## 动态 RTT 与时钟

Controller 每0.5秒复用现有不可靠探测，按本机保存的发送时刻与应答序号计算 RTT。SRTT 用1/8权重平滑，RTTVAR 用1/4权重平滑相对旧 SRTT 的绝对残差；RTTVAR 不是统计方差。样本包含服务器与客户端的调度、排队时间，不能当作纯链路时延。排队样本反映往返变化，但不能拖偏质量更好的时钟偏移。

最多保留8个待应答样本。未知、重复、乱序及非法应答不能更新估计；超过5秒没有有效观测则失效，新合法样本重新建基线。客户端诊断每秒记录 `ProbeRttFresh`、`ProbeRttMs` 与 `ProbeRttVariationMs`；没有有效值时记为不可用，专服不把客户端测量当作自己的 Ping。

这属于应用层动态测量，UE 原生可靠传输仍负责自己的确认和重传。本轮未另写 UDP/RTO，也没有据客户端 RTT 放大服务器射击时间窗。RTT/2 依赖上下行对称假设，不能保证真实单向时延。

## 冻结的工程预算

具体阈值以 [FpsNetworkBudgets.json](../Tools/Networking/FpsNetworkBudgets.json) 为准。这些是本项目的验收目标，不是所有商业 FPS 的统一标准，也不是已实现容量的声明。

容量使用同机 Editor 专服、独立 NullRHI 客户端、正式场景与真实 160 AI。服务器目标 30Hz，客户端固定 60Hz，按 2/4/8 人逐级验证。客户端通过正常 CMC/GAS 输入移动与朝安全方向连射；正式射线和 AI 仍运行。大血量、一次性充足初始备弹仅维持受控负载，不禁用伤害、不逐帧补给。该场景不证明多人对射公平性或渲染平滑。

| 指标 | 工程目标 |
| --- | --- |
| 正常网络本地预测到最终 ACK P95 / P99 | ≤150 / 250ms |
| 每端出站模拟 100±20ms、5%丢包时 P95 / P99 | ≤400 / 650ms |
| 非预期拒绝、缺失终结、重复执行 | 0 |
| 每条服务端连接出站 / 客户端出站 | ≤64 / 16KiB/s |
| 每条连接出站包量 | ≤100 包/s |
| 专服 World Tick 线程 CPU P95 | ≤22ms |
| 专服 TickFlush 作用域 P95 | ≤6ms |
| 专服帧间隔 P95 | ≤40ms |
| 客户端位置纠正 | ≤2次/s |
| 正式容量结论 | 至少3轮、每轮≥40s、有效覆盖≥95%、无Trace |

模拟参数不是实测 RTT。一次短探测只验证流程；某个人数失败时保留失败并报告边界，不降低人口或放宽阈值后称为原目标通过。

## 采集口径

- 字节和包量来自每条真实 `UNetConnection` 累计计数差分，包含引擎协议与开销计数，不是网卡抓包或单个 Actor 的独占流量。连接替换、累计计数倒退或缺失会使对应样本无效。
- `WorldTickCpuMs` 用 Windows `GetThreadTimes` 测量该 World Tick 的线程执行 CPU；不包含其他线程，也不是复制系统独占 CPU。原生计数可能存在时间量化，保留原始值，不把单帧数值称为亚毫秒精度。
- `ReplicationTickFlushMs` 来自引擎原生性能消费者，是 Driver 的墙钟作用域，可能包括调度等待。UE5.5 在下一帧消费它，按实际帧号回填后再统计。
- `PacingIdleMs` 与 `IdleOvershootMs` 区分主动限帧等待和超出请求的等待；超睡与 OS Ready/Blocked 调度原因不能直接画等号，后者仍需调度追踪或单变量对照。
- 捕获窗口内缓冲逐帧采样，窗口结束后写盘，避免逐帧日志 I/O 改变负载。计数端点共用同一本机单调时间。缓冲溢出、低覆盖、人数或人口变化均失败。
- STOP 只结束计量和新输入，DONE 还要求在途射击、服务器执行队列和换弹收尾。不能刚停止输入就杀进程，再把缺 ACK 当成网络问题。
- 业务确认时延使用同一客户端的单调时钟；不同进程的单调时钟不能相减。跨机单向延迟没有校时证据时保持未知。
- NetTrace 与 CPU Trace 是另一次诊断，不能代替无 Trace 容量结果。包/Bunch 的原始编号、可靠重发和业务书签保留在证据中。

## 已定位的问题与取舍

2026-10-25 改动前的严格弱网诊断记录在 `Saved/FpsNetworkClosure_20261025/BeforePacketDiagnosis_R2.json`：同一可靠 Bunch 679 首次在包11481丢失，267.979ms后在新包11500重发成功。后续 Bunch 680/681 已提前到达，却等待补洞后才执行，分别等待186.848/47.724ms。期间其他不可靠 Actor 数据继续到达，不能称为整条连接阻塞。

该诊断的 ShotId 对应来自提交顺序，未直接解码 RPC 参数；原始包、内容位范围与限制一并保留。首轮归档还出现 Trace 文件锁错误，日志和失败保留，不补写成完整通过。

另一次渲染客户端启动时首个时钟样本 RTT 约537ms，随后约29ms的优质样本仍被旧估计缓慢拖动，导致实际约24ms到达的首发被估成134ms。修复应改进样本选择与校准，而不是扩大服务器允许的历史时间窗。

改成不可靠输入窗口后的诊断中，113个 `ServerSubmitShotBatch` 均由不可靠 Bunch 承载，旧 TargetData 射击调用为0。该轮37发全部接纳并完成，但最终确认 P95 仍达492ms。原始下行 Trace 证明可靠结果 Bunch504 首包7034丢失，321ms后重发成功；后续505/506已先到，却额外等待185/94ms。书签和日志顺序可关联到射击35/36/37，未直接解码 RPC 业务参数。

因此输入与结果两个方向分别验证：输入不能被逐发可靠重传堵住；结果以同一服务器终结事实快速送达，同时保留可靠兜底。客户端只消费一次终结、重复收据不能重复退款或生成表现；迟到的属性基准仍受独立版本控制。快速收据仍可能丢失，不把传输冗余称为第二套命中或伤害实现。上述具体实现的正式预算结果另行记录。

单发快速副本的下一轮诊断又暴露了自身丢包：射击2和10的快速/可靠 Bunch 虽然可靠位不同，却装在同一数据报中一起丢失，仍要等约323–327ms后的可靠重传。因此快速结果携带最近最多4条已经终结的裁决，让下一次结果可以顺带补齐前面的收据，不增加另一套结算、重发定时器或无界缓存；停止射击后的尾部仍由可靠回执保证收口。4条是待带宽与时延实测检验的有界配置，不是任意丢包下的延迟保证。

高速横移专项在第一轮中命中失败；改用真实胸部查询形状中心、统一帧末采样后仍失败，未把这些修改当作已验证的根因。记录显示显示点与历史查询体相差约59–67cm，固定缓冲与 RTT 估计不足以证明实际显示时刻。原生显示时间方案需通过同一发、同一目标的两端时间（误差≤1.1ms）与实际扣血配对，不能仅靠请求已接纳或枪声已播放认定命中正确。

最终构建、完整回归、正常/弱网对照、同进程断包恢复与容量上限应分别记录；最新结果统一由本轮报告索引引用，本文不将实现或历史成绩自动视为本轮通过。

## 工具入口

2026-10-26 最新白名单摘要见 [本轮实测](Testing/fps-network-20261026.json)。97项完整回归与分项功能测试通过，同时保留弱网+渲染+横移组合失败，以及未通过容量预算的诊断。

最后一次160 AI、双客户端、20秒带Trace诊断，显式丢弃首发所在的一次真实出站数据报：客户端通道11的可靠Bunch899首包19117丢失，259.9003ms后由包19129重传成功。期间服务器已执行七次不可靠射击批次，但尚未收到同一能力激活，均未获授权。这里证明的是业务依赖等待；没有证明该区间还存在后续可靠RPC的队头阻塞，也未直接解码RPC参数。输入不能绕过授权，因此这是当前未消除的体验边界。

该诊断Client1共82次预测，75接纳、7拒绝，其中1次缺失输入终结，0缺失ACK；同轮后期其他拒绝未一并归咎首发注入。Client2共81次均接纳。这轮有Trace、主动故障且仅20秒，不认证正式容量。原始记录、失败门槛和证据限制均保留。
