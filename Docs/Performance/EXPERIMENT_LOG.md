# 性能优化实验记录

记录更新：2026-09-18。覆盖采集日期：2026-08-16～09-16。

本文按 13 组记录保留成本定位、策略验证、同步归因与候选选择的完整过程，各组记录测试条件、结果、决策和原始证据目录。早期逐组明细见 [PERFORMANCE_EVIDENCE.md](../../PERFORMANCE_EVIDENCE.md)，策略与消费者关系见 [README](../../README.md#性能优化架构)。

## 结论摘要

 80 敌人各三次对照支持 Movement 分级、Animation Sharing、阴影参与限制和骨骼 RT 参与限制的局部收益，分别为 0.189、0.408、0.721 和 0.296 ms；不同消费者与线程的收益不能相加。后续 0/160 对照、任务事件与查询干预把一类 RT 长等待追到历史遮挡查询结果同步，修正了“停在动态网格收集就是 Mesh 计算太重”的初始判断。当前工作已从敌人消费者优化推进到 GPU 工作分解与候选验收。

调查主线是：**人数增加时哪些工作变贵 → 保留玩法能否少做重复工作 → 局部成本降低后为何整帧仍慢 → 零敌人是否仍等待 → 等待的任务又依赖谁 → 改查询策略是否转移成本 → 哪些 GPU 子项值得继续优化。** 下文按问题衔接整理既有记录，不将 AI 与渲染支线表述为严格的开发先后。阶段 6 属于测试条件记录，不计入性能成果；执行异常只用于判定数据能否参与对照。

## 记录口径

- 时间单位统一为 ms，次数、人数和内存另行标注。多轮均值按运行等权汇总；多轮 P95/P99 是各轮分位数的平均，不是把所有帧合并后重新计算的分位数。
- **历史诊断口径**：早期 Runner 排除了 HUD、声音和玩家受伤，只用于相同旧口径的策略对照，不代表完整玩法。
- **完整玩法口径**：保留正常 HUD、声音、伤害/死亡和其他消费者；死亡或提前结束使采集无效。
- **固定场景成本口径**：后续渲染实验保留 HUD、声音与伤害调用，但把玩家生命覆盖为 1000000，并锁定输入和视点。用于延长成本采样，不等于正常生命条件下的玩法回归基线。
- 关闭分级通常使更多对象全量更新；关闭整个组件 Tick 或渲染参与则会删除工作。两类消融方向不同，不能混用“关闭优化”和“关闭功能”。
- CSV 的 `Exclusive/RenderThread/EventWait/Visibility` 是等待代理，不等于精确的 `WaitForGatherDynamicMeshElements` scope。CPU/RHI 与 GPU 上同名 BLAS 事件必须分开解释，父子 Timer 和并行线程时间不能相加成整帧成本。
- 原始文件保存在本机工程 `Saved/Profiling/`，不随公开仓库分发。下列证据目录均相对该目录；公开文档保留摘要和可定位的文件名，不生成指向未分发数据的网页链接。

## 阶段 1｜规模压测与生命周期检查（08-16）

**为什么先测规模。** 起点只知道多人场景慢，还不能确定先改逻辑还是渲染。因此先不调整算法，在固定地图和分辨率下逐级增加敌人，观察哪些工作随人数增长。原矩阵包含 10/20/40/80/160，以下选取代表规模；每档只有一次运行。

| 敌人数 | Frame | GT | CharacterMovement | Animation |
| ---: | ---: | ---: | ---: | ---: |
| 20 | 16.352 | 5.879 | 0.745 | 0.977 |
| 80 | 18.115 | 16.106 | 3.231 | 2.728 |
| 160 | 27.907 | 27.899 | 6.188 | 4.448 |

160 敌人同时记录到 AI Decision 0.201 ms、MoveTo 14.565 次/帧。移动与动画随规模明显增长，160 敌人的 GT 超过 16.67 ms，但规模对照不能证明具体优化参数有效。

**生命周期支线。** 80 敌人全部清理后，Enemy Actors 从 80 归零，UObject 从 50763 降至 49876，Movement 从 3.705 降至 0.106，Animation 从 2.915 降至 0.266，GT 从 18.110 降至 5.444。Frame 从 22.242 降至 14.596。进程物理内存反而从 3616 MB 增至 3676.34 MB，因此只能确认对象数量及持续工作下降，不能判定立即返还内存或已消除泄漏。该批有 41 条 CharacterMovement 最大迭代次数告警，VSM/纹理池告警为 0。

**决策与下一步。** 移动和动画成为优先调查对象，但人数增加会同时改变很多工作，相关性还不能区分直接成本与下游连带成本。因此下一步进入调用链，逐项停用类别验证。内存支线仍需出生/死亡循环和分配生命周期跟踪，单次清理不作为泄漏验收。

**证据。** `FPS_FinalLOD_20260816/summary.md`；`LifecycleCleanup_80_20260816/summary.md`。

## 阶段 2｜调用链与成本上界（08-24）

**承接规模测试。** 移动和动画随人数明显增长，但 GT 总值还包含子任务与等待。先用 Insights 检查约 413 帧稳定区间，再独立关闭 Movement、PathFollowing、SkeletalMesh Tick 等类别，检查执行次数与局部时间是否同步减少；关闭只是归因工具，不是交付方案。

初始 Trace 的近似每帧成本：GT CharacterMovement 3.3、动画并行求值完成 2.8、GT 任务等待 4.7；RT 动态光追实例收集 2.35、完成等待 1.50；RHI 动态光追几何更新 Inclusive 8.96、BLAS 事件总计约 9.88；Worker RayTracingMeshBatchTask 2.74。Timer 有嵌套和重叠，不能相加。攻击 Sweep 约 0.008，AI 更新自身约 0.08，并非该批最重的局部函数。

| 诊断开关 | 工作量变化 | 观测结果 | 边界 |
| --- | --- | --- | --- |
| Movement Tick Off | 149.5 → 1 次/帧 | Movement −5.103；GT −13.495 | 破坏正常移动，包含下游变化 |
| PathFollowing Tick Off | 160 → 0 次/帧 | Movement −3.792；GT −12.822 | 不能把 GT 差值当作 PathFollowing 自身成本 |
| SkeletalMesh Tick Off | 162 → 2 次/帧 | Animation −3.252；GT −9.434 | 破坏动画、Socket 更新与攻击表现 |
| Attack Sweep Off | 对应执行归零 | 仅约 0.006～0.008 | 不列为主要目标 |
| Pawn Collision Off | 敌人 Capsule 对 Pawn 通道设为 Ignore | 无稳定正收益 | 同时影响玩家 Pawn，不支持以删除碰撞作为方案 |

**决策与下一步。** 关闭实验仅用于确定成本上界。正式策略改为更新降频、姿态共享和消费者参与限制，保留正常移动与攻击。

**证据。** `InsightsFirstDiagnosis_20260824/Baseline.utrace`、`InsightsExport/`；`EnemyBottleneckDiagnostics_20260824_MovementFollowup/`；`ProfileGuidedAblation_20260824/`。历史 `InsightsLoaded.png` 实为浏览器截图，已排除其证据用途。

## 阶段 3｜AI 决策降频与群体约束（08-24 历史消融）

**为什么检查 AI 降频。** 上一轮 AI 函数自身并非最重热点，但决策仍是下游路径请求的入口。本轮验证减少重复决策能否同时减少请求，而不是预设换 Timer 接口就会更快。单个 AI 采用一次性 Timer，根据状态和距离选择下一轮间隔，并错开首次更新；战斗附近保留短间隔。

现有群体架构还包括共享目标、稳定槽位、攻击许可、目标去重、失败退避与请求预算；这些机制不由本节实验分别验证。以下历史对照只测试 AI 降频开关：160 敌人，AllEnabled / NoAIThrottling 各三次。

| 指标 | 启用降频 | 关闭降频 | 启用后的变化 |
| --- | ---: | ---: | ---: |
| AI 决策/帧 | 19.521 | 56.741 | −65.6% |
| AI Decision | 0.215 | 0.726 | −0.511 |
| Move Requests/帧 | 16.063 | 52.897 | −69.6% |
| GT | 28.179 | 37.081 | −8.902 |

**结果与边界。** 决策次数、局部时间与路径请求三项同向，支持降低决策频率。它不是 Timer API 对 Tick API 的独立性能比较；GT 差值包含寻路、移动及等待等连锁效应，不能全部归于 AI 函数。

0.1/0.25/0.5/1 s 的基础间隔、档位倍率、8 个攻击许可、8+12 个槽位、每帧 8 次 MoveTo 中预留 2 次近战请求，都没有通过该批实验分别证明最优。当前架构关系见 README，不能把后续策略组合的收益倒算为早期某一个机制的收益。

**决策与下一步。** 调用量、局部时间与移动请求同向下降，保留决策分频。但减少决策不会自动降低持续运行的移动、骨骼更新成本，因此下一步分别管理并验证消费者。群体约束承担玩法稳定性与请求控制，不分配未经独立消融的毫秒收益。

**证据。** `EnemyOptimizationAblationSeed1337_20260824/`；早期明细的“AI 更新节奏”章节。

## 阶段 4｜规模复测与运行间波动（08-30，09-01 补 Trace）

**为什么分开玩法与渲染。** 屏幕外敌人仍可能攻击玩家，不能按相机可见性降低全部玩法响应；攻击骨骼必须及时更新，也不等于必须获得更多阴影和光追名额。因此分层 Significance 将玩法距离/攻击规则与相机相关渲染分级拆开，战斗动画另行保护。接入 Movement 分级、Animation Sharing、LOD、动画更新及阴影/骨骼 RT 限制后重新测规模。该阶段仍是旧诊断口径，每档一次，不是跨版本严格 A/B。

| 敌人数 | 初轮 Frame / P95 / P99 | 热缓存轮 Frame / P95 / P99 | 热缓存轮 GT / RT / RHI |
| ---: | --- | --- | --- |
| 20 | 28.711 / 54.754 / 94.569 | 20.359 / 33.290 / 36.665 | 4.532 / 19.985 / 16.568 |
| 80 | 45.350 / 148.134 / 163.594 | 14.023 / 25.712 / 34.063 | 6.273 / 13.650 / 10.772 |
| 160 | 29.983 / 33.850 / 60.620 | 30.899 / 37.975 / 40.562 | 7.707 / 30.411 / 27.593 |

与 08-16 的 160 敌人相比，后期热缓存样本的 GT 为 27.899 → 7.707，Movement 为 6.188 → 1.636，Animation 为 4.448 → 0.814；AI Decision 为 0.201 → 0.039，MoveTo 为 14.565 → 0.109 次/帧，但 Frame 为 27.907 → 30.899，未同步改善。二进制和预热条件不同，种子一致性也未建立，因此这些只是组合策略的跨版本趋势，不归于某个 Significance 或请求预算参数，也不能只选热缓存较快的一轮宣称稳定提速。

09-01 另采 160 敌人 Trace：预热 15 秒、采集 10 秒，704 个有效 CSV 采样。Frame/GT/RT/RHI/GPU 的 P95 分别为 15.280/9.280/14.830/12.490/9.420，CSV 可见性等待代理 P95 约 4.650。该次运行比部分规模矩阵快，但不是同一轮，也不能替换较慢样本。

**决策与下一步。** 这里留下两个问题：组合策略中每一项究竟省了什么，GT 较低时整帧为何仍慢。先用同批“消费者数量 + 对应局部时间”的单变量实验回答前者；后者保留到 RT/RHI 依赖调查，不用跨版本总值分配单项收益。

**证据。** `CurrentScaleMatrix_20260830/summary.md`；`CurrentScaleMatrix_Warm_20260830/summary.md`；`Current160Insights_20260901/Baseline.utrace` 与 `InsightsExport/`。可公开截图：[160 敌人 Insights](../../PerformanceEvidence/UnrealInsights_160Enemies.png)。

## 阶段 5｜消费者重复消融（08-31）

**为什么逐项关闭策略。** 组合版本同时改变多项工作，RT/RHI 又有运行间波动，单看总 FPS 无法归因。因此固定一个版本，保留其他策略，每次只关闭一项，确认其消费者和目标时间如何变化；关闭预算是恢复更多对象参与，不是删除对应功能。

Demonstration、80 敌人、1600×900、VSync Off、seed 1337、预热 10 秒、采集 30 秒；默认组加六个单变量关闭组，各三次、随机组顺序。仍使用旧诊断口径。各次初始生成有 16 次可恢复重试，最终 requested=alive=80，VSM/纹理池告警为 0。

| 策略 | 启用时消费者 → 关闭策略后 | 局部耗时：启用 / 关闭 | 启用后的局部收益 |
| --- | --- | --- | --- |
| Movement 分级 | 65.1 → 81 次 Tick/帧 | 1.056 / 1.245 | 0.189，15.2% |
| Animation Sharing | 60.6 → 0 个 Follower | Animation 0.818 / 1.226 | 0.408，33.3% |
| 阴影参与限制 | 5 → 80 个投影敌人 | ShadowDepths 1.052 / 1.773 | 0.721，40.7% |
| 骨骼 RT 参与限制 | 12 → 80 个参与敌人 | GPU Skinned BLAS 0.199 / 0.495 | 0.296，59.8% |

四项目标局部耗时均三次同向。阴影限制另使 Shadow Draw Calls 从 1013.4 降至 637.0（−37.1%），总 RHI Draw Calls 从 2111.8 降至 1655.0（−21.6%）。这些结果来自不同消费者与线程，不相加成整帧收益。

**未建立收益的策略。** Skeletal LOD 分配约从 19.4/28.7/31.8 变为 80/0/0，机制生效；但启用/关闭的 Animation 为 0.818/0.805，GPU Skinned BLAS 为 0.199/约 0.193，无独立正收益，骨骼 RT 驻留内存也无稳定改善。

动画 Tick 分级追加默认/关闭各四次紧配对：Animation 0.795/0.824，GT 6.729/6.558，Frame 28.535/24.049，RT 28.067/23.568，RHI 25.148/20.598，GPU 9.048/9.622。关闭组 Frame 范围约 18.85～28.00，差异主要落在 RT/RHI，不能把 0.029 ms 包装为稳定净收益，也不能把整帧差值直接判为动画分级的因果负收益。

默认 `RayTracingBudgetRejected=0`：Full Render 上限 12 已把 RT 候选限制到最多 12，独立 RT Top12 未再次筛人。该实验验证的是整体 RT 参与限制，不是独立 Top12 配额的收益。

**决策与下一步。** 保留四项已验证的局部机制；LOD 和动画 Tick 分级标为待标定。30/20 Hz、共享 Leader 数、Top5/Top12、权重与距离阈值均不宣称最优。优先解释 RT/RHI 等待，再决定是否投入固定姿态的 LOD/画质专项。

**证据。** `UnverifiedConsumers80_20260831/analysis.md`、manifest、逐轮/分组汇总与截图；`AnimationTierConfirm80_20260831/`。逐轮原始数值区间保留在早期明细中。

## 阶段 6｜完整玩法口径迁移（截至 09-05）

**问题与策略。** 旧 Runner 的 HUD、声音和受伤排除使历史数字不能代表完整玩法。迁移后禁止移除 Widget，恢复正常生命、声音和伤害/死亡，移除基准专用强制重叠生成；不传任何破坏性关闭参数。

**长采集结果。** 160 敌人生成完后，静止玩家约 3.7～5.4 秒内死亡，15 秒预热 + 30 秒采集被判无效。不以重新关闭伤害补齐样本。

**短链路验证。** 零预热、2 秒采集三次，101/110/104 帧，共 315 帧。运行级平均如下：

| Frame | Frame P95 | Frame P99 | GT | RT | RHI | GPU |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 15.473 | 17.277 | 17.603 | 9.305 | 15.464 | 10.026 | 13.964 |

GT 单轮范围 8.748～10.380，Frame 14.762～16.114。这只通过采集链路冒烟，不替代稳态基线，也不与历史 7.707 ms 做单变量比较。

**零敌人与短贡献补测。** 零敌人单次预热 15 秒/采集 30 秒，1312 帧：Frame 22.606、P95 33.540、P99 35.769、GT 6.179、RT 22.107、RHI 15.006、GPU 12.047；等待代理 5.238、约 1111 Draw Calls。它不能与 160 敌人 2 秒冒烟直接相减。

随后 0/160 各三次交错 2 秒采集：零组预热 10 秒，160 组用生成阶段约 10 秒作自然预热；Gameplay 历史并不等价。0/160 的 Frame 为 31.593/32.631，GT 9.618/19.014，RT 32.045/32.748，RHI 11.337/15.653，GPU 14.608/15.645，Draw Calls 1793/2837，本地显存 3286.7/3506.0 MB。另一次 160 运行因死亡被排除；零组 Run1 有约 451 ms 起始异常帧，本组 P99 不用于归因。详细局部增量见早期明细。

**决策与下一步。** 正常生命长期基线需要可重复的玩家移动/战斗回放，尚未验收。渲染归因改用单独标记的高生命固定场景口径，不能将其名称中的 Baseline 理解为完整玩法基线。零敌人同样有高 RT，继续定位同步链。

**证据。** `PerformanceBaseline160_FullGameplay_Smoke/`、`PerformanceBaseline160_FullGameplay_Smoke_R2/`、`PerformanceBaseline160_FullGameplay_Smoke_R3/`；`PerformanceBaseline0_FullGameplay_20260905/`；`FullGameplayEnemyContributionAligned_20260905/`。

## 阶段 7｜Detour 候选与残余敌人渲染成本（09-08）

## 阶段 9｜把 RT 等待追到遮挡查询同步（09-09）

**为什么新增 TaskTrace。** 零敌人也有等待，CSV 却只能记录耗时；已有 Trace 的 Gather 名称只说明 RT 在等什么完成，没有说明 Worker 为何迟迟不完成。因此沿任务依赖追上游，而不是继续按 Timer 名称猜成本来源。

0/160 各新增一次 TaskTrace，预热 15 秒、采集 20 秒。排除捕获区间首 1 秒和末 0.5 秒，对照 RT、Worker、RHIInterruptThread：先查等待区间重叠，再匹配任务 ID 与 Completed 通知关系，最后用本地源码解释查询及手动管道如何连接。

**结果。** 两次 Frame 为 13.637/15.574，属于另一批诊断，不与阶段 8 相减计算收益。RT 等待 scope 数为 1366/1199，`WaitForGatherDynamicMeshElements` 平均 5.123/5.368；与查询 `SyncPoint_Wait` 的时间加权重叠为 95.76%/95.24%。

```text
RenderThread 等待 GatherDynamicMeshElements 完成
  → 动态网格管道仍依赖上游可见性处理
  → OcclusionCullPipe 的 Worker 等待查询结果 SyncPoint
  → GPU fence 支撑的结果可用性同步由 RHIInterruptThread 通知
  → Worker 和后续管道推进，RenderThread 结束等待
```

不仅比较时间重叠：0/160 各选 median、P95，共 4 个代表样本，核对通知线程与具体 TaskId；通知后至 RT 等待结束分别为 0.2221/0.2292/0.3539/0.2145 ms。证据支持遮挡查询结果同步位于本批关键路径，不支持“某个敌人 Mesh 自己计算了整个等待时长”。

**限制与下一步。** 尚未绑定具体 query/payload/fence 到某个 GPU Pass，也未重建所有手动管道依赖边。95% 重叠不是某个资产的成本占比，更不是遮挡查询 GPU Pass 的执行时间。下一步只改查询开关，验证等待是否消失及代价转移。

**证据。** `RenderWaitTaskTrace_20260909/render_wait_diagnosis.md`、`task_dependency_audit.md`、`summary.md`。

**历史现场补证。** 新找回的原图 R01 显示 RT Frame 16052 为 17.4 ms、Gather 等待为 8.3 ms，Callers/Callees 中另有 GT 等待 5.3 ms；R02 显示另一个 RHI 帧的动态光追几何更新 5.5 ms、BLAS 范围 4.9 ms。两图直观呈现了需要调查的等待和 RHI 成本，但不是本阶段 0/160 的正式 TaskTrace。95.76%/95.24% 及通知顺序仍来自上列事件审计，不能把这些历史截图当成它们的单帧图证，也不能将 RHI CPU 范围写成 GPU BLAS 耗时。

零敌人、固定镜头，只改进程内 `r.AllowOcclusionQueries`，顺序 On/Off/On/Off；预热 15 秒、采集 20 秒，共 4/4 有效。首次试跑的校验只认 `1`、不认引擎回显 `true`，因此被排除并另目录重跑，不是游戏崩溃。

## 阶段 13｜GPU 分辨率探索（09-16）

**为什么先用分辨率诊断。** 查询同步已定位到 GPU 结果可用性，但尚不知道哪些 GPU 工作影响到达时刻。降低内部渲染分辨率会影响多类像素相关工作，适合先筛选哪些范围随之变化，再做单项归因；不是直接决定降低交付画质。

保持输出 1600×900，仅比较默认分辨率策略与显式 `r.ScreenPercentage=50`；160 敌人、RVO、硬件查询、HZB=0、Buffer=1，预热 15 秒、采集 15 秒，各一次且同样开启 Task/GPU Trace。

`r.ScreenPercentage=0` 表示采用默认策略，不是 0% 或已验证的 100%。DLL、地图、DefaultEngine/DefaultGame 与启动前 GameUserSettings 指纹一致，但没有取得实际内部渲染宽高证据；不以反推比例代替实测。

**有效性限制。** 两次原始 manifest 均为 `Valid=false`，不纳入正式基线或候选验收：

- 各有 32 次 Ready 前生成重试，最终完成 160，采集期间没有掉人数；不能擅自放宽原门禁并把旧数据改成通过。
- B 的隔离检查还在退出后把本轮自身 PID 误判为竞争进程；报告核对 77 次观测，未发现运行中外部进程冲突。后续脚本修正不改变该次原始标记。
- 检查点视点漂移为 0、阴影/RT 数量为 5/12，但固定种子不保证战斗姿态一致：采集开始的 Movement Full 为 57/49，Mesh Tick 为 17/16，Draw Calls 也不同。

**决策与下一步。** 不修改默认分辨率、不宣布 GPU 优化验收。优先分别诊断照明根 scope 下的反射与 Screen Probe Gather，核实实际内部分辨率，再重复平衡顺序。若仍需回答队列空档和哪次提交解除查询等待，补 GPU 队列/fence 证据，而不是凭相邻事件时间猜测。

| 3 | 完成 Buffer2 候选验收 | 补合格 Hardware 对照，必要时重建同批配对；检查快速转镜和遮挡变化，不以原等待缩短单独通过 |
| 4 | 完成正常生命的 160 敌人回归基线 | 接入可重复玩家操作，维持正常伤害/死亡、HUD、音画和玩法；固定视点高生命样本不替代该基线 |
| 5 | 内存与生命周期专项 | 多轮出生/死亡/回收，结合 UObject、分配记录及进程/显存趋势；区分缓存高水位与持续增长，现有单轮数据不足以宣称无泄漏 |

已完成的是敌人消费者的部分局部验证，以及 RT 等待从表面动态网格 scope 到遮挡查询同步的归因。尚未完成的是正常玩法长期基线、GPU 高成本子项的正式优化验收、Buffer2 最终选择和系统性内存诊断。当前没有把所有 Significance 参数视为最优，也没有以单个 GT 数字证明稳定 60 FPS。
